2. Tidy data: variável, observação e unidade observacional

INÍCIO DA CONSULTA — Aula 2 · seção 2 — Tidy data: variável, observação e unidade observacional

Na prática anterior, observamos duas tabelas chapadas do GBIF sem classificá-las formalmente como tidy ou não tidy. Agora voltamos às mesmas tabelas para avaliar se linhas, colunas e células estão organizadas de forma coerente com a unidade que queremos representar.

Base conceitual — Wickham (2014). Cada variável ocupa uma coluna; cada observação ocupa uma linha; cada tipo de unidade observacional ocupa uma tabela. Abrir o artigo disponível no pacote.

2.1 Como reconhecer uma tabela tidy

Identificar a unidade observacional começa por perguntar o que uma linha representa. No GBIF Simple, uma linha representa uma ocorrência; na lista taxonômica agregada, uma linha representa um táxon resultante da agregação. Tidy data não pergunta se existem valores repetidos: pergunta o que cada linha representa, o que cada coluna representa e como os valores estão organizados nas células.

2.2 Aplicando tidy data ao GBIF Simple

País, instituição, localidade ou classificação taxonômica podem se repetir em diferentes ocorrências sem que isso, por si só, viole tidy. O arquivo real, porém, contém campos multivalorados. issue reúne diferentes sinalizações do GBIF separadas por ponto e vírgula; em alguns registros, recordedBy e identifiedBy também codificam listas de agentes.

Diagnóstico tidy — não estritamente tidy em todos os campos. A unidade da linha é clara e a maior parte da estrutura segue a lógica tidy. Entretanto, quando a finalidade exige analisar separadamente cada sinalização ou cada agente, os campos multivalorados precisam ser desdobrados.

2.4 Quando uma tabela não é tidy?

O problema não é simplesmente repetir um valor em várias linhas. A estrutura deixa de seguir a lógica tidy quando a mesma variável é espalhada em colunas como species1, species2 e species3; quando uma célula codifica vários valores que precisam ser analisados separadamente; quando uma linha reúne mais de uma observação da unidade que deveria representar; ou quando tipos diferentes de unidades observacionais são misturados sem uma unidade de linha clara.

2.5 Quando unidades observacionais diferentes exigem tabelas diferentes

Nem toda tabela chapada precisa ser dividida. A separação passa a fazer sentido quando precisamos representar tipos diferentes de unidades observacionais. Na biblioteca, livros, autores, pessoas e empréstimos são unidades distintas; em dados biológicos, também podemos precisar distinguir organismo, acontecimento, material coletado ou outra unidade.

Ideia central — Reconhecer a unidade observacional é essencial para decidir como organizar os dados. Quando existem diferentes tipos de unidades observacionais, pode ser necessário representá-las separadamente para preservar com clareza o que cada linha representa. Na próxima seção, partiremos dessa organização das unidades para construir um modelo de dados usando o exemplo de uma biblioteca.

5.1 Evidências reais de meta.xml: rowType, id, coreid e termos

INÍCIO DA CONSULTA — Aula 2 · seção 10.2 — Do meta.xml ao relacionamento entre as tabelas

Leia cada trecho da esquerda para a direita: rowType declara o tipo de linha; location nomeia o arquivo; id identifica a chave do core; coreid declara a coluna da extensão que aponta para o core; e field mapeia uma posição física para um termo.

Core Occurrence

<core ... rowType="http://rs.tdwg.org/dwc/terms/Occurrence">
  <files><location>occurrence.txt</location></files>
  <id index="0" />
  <field index="0"
    term="http://rs.gbif.org/terms/1.0/gbifID"/>
</core>

Interpretação: cada linha do core representa uma Occurrence; a coluna física 0 é simultaneamente o identificador estrutural do core e o campo mapeado para gbifID.

Extensão verbatim

<extension ... rowType="http://rs.tdwg.org/dwc/terms/Occurrence">
  <files><location>verbatim.txt</location></files>
  <coreid index="0" />
  <field index="0"
    term="http://rs.gbif.org/terms/1.0/gbifID"/>
</extension>

Interpretação: a coluna 0 não cria outra PK independente; ela referencia o id do core. Neste download há uma linha verbatim para cada ocorrência.

Extensão Multimedia

<extension ... rowType="http://rs.gbif.org/terms/1.0/Multimedia">
  <files><location>multimedia.txt</location></files>
  <coreid index="0" />
  <field index="0"
    term="http://rs.gbif.org/terms/1.0/gbifID"/>
  <field index="3"
    term="http://purl.org/dc/terms/identifier"/>
</extension>

Interpretação: várias linhas podem repetir o mesmo coreid. Essa repetição representa várias mídias ligadas a uma ocorrência, não duplicação indevida da FK.

6. Síntese para interpretação

Tabela chapada

  • Leitura direta e filtros simples.
  • Atributos de várias entidades repetidos.
  • Contar linhas pode confundir ocorrências, espécies ou relações.
  • Correções podem precisar ser repetidas.

Tabelas relacionais

  • Cada tabela preserva sua unidade de registro.
  • PK identifica; FK reconstrói a ligação.
  • Extensões podem ter zero, uma ou várias linhas por core.
  • Integridade referencial deve ser verificada.

Fundamentação e referências desta exploração

  • Wickham (2014): variável em coluna, observação em linha e cada tipo de unidade observacional em uma tabela. O explorador mostra por que isso pode resultar em uma tabela chapada ou em várias tabelas relacionadas. Abrir PDF.
  • Elmasri & Navathe: fundamento de chaves, cardinalidades, integridade referencial e JOIN. A obra é citada, mas não redistribuída por restrição autoral; consulte o índice de referências.
  • Darwin Core Text Guide: papel estrutural de id, coreid, core e extensões no meta.xml. Abrir documentação oficial.
